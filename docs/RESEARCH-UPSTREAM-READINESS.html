Research brief · rampscan

Upstream Readiness

What contributing to FedRAMP's open source actually means, whether rampscan is ready for it, and what "FedRAMP-appropriate UI" turns out to require.

12 September 2026 · Verified against FedRAMP/schemas, FedRAMP/rules, FedRAMP/2026

The short answer

FedRAMP's repositories do not merge outside code. Across the four active repos, every merged pull request came from a FedRAMP staff account. Three external pull requests exist; none were merged.

But outside findings do land. One contributor filed an issue describing two schema defects found while building a provider tool, plus a pull request fixing them. The pull request was closed unmerged. Both defects were then fixed by staff pull requests, and the issue was closed.

So the contribution is the diagnosis, not the patch — which is precisely what rampscan is built to produce.

The case that matters

Issue #3 on FedRAMP/schemas, opened by an outside contributor, reports that the 2026-06-24 schemas carry unresolvable cross-document $refs and that finalDisposition has no remediated value. The opening line describes where the defects came from:

“Both were found while building a provider tool that generates the CR26 vulnerability report from live system state and validates…”

Their pull request (#4) was closed unmerged on 17 July. Their issue stayed open. On 1 September it was closed — after staff pull request #15 fixed the $ref form and #22 added the remediated disposition value.

The finding was adopted; the code was not. That is the entire playbook, and it describes rampscan's position exactly: a tool that validates real documents against the published schemas and can therefore say precisely where they are wrong.

Where contribution is actually invited

  • RFC comments. FedRAMP publishes proposed changes at fedramp.gov/rfcs with roughly 30-day windows, taken on GitHub Discussions. They ask for "explicit targeted feedback rather than general commentary."
  • Issues against schemas and rules, as demonstrated above. schemas currently has exactly one open issue and no open pull requests.
  • Publishing your own implementation. The established pattern is a self-owned repo — Paramify, Knox, Anitian and Confluent each published their own 20x pilot submission rather than contributing into FedRAMP's repos.

“UI/UX as per FedRAMP” — what that actually means

The assumption to check before spending a week on it

The U.S. Web Design System does not apply to rampscan. USWDS and the 21st Century IDEA govern federal agency public-facing websites, and reach contractors through contract language when they are building those sites. rampscan is a provider-side tool. Nobody will require USWDS of it.

More to the point: FedRAMP's own CR26 site isn't USWDS either. FedRAMP/2026 builds a static documentation site with Zensical and MkDocs — breadcrumbs, a nested sidebar, an on-this-page rail, anchor-linked sections. Clean technical documentation, not a federal design-system implementation. Imitating USWDS would make rampscan look less like FedRAMP's ecosystem, not more.

What does apply

Section 508 incorporates WCAG 2.0 AA, and USWDS itself targets 2.1 AA. This matters for rampscan not as a mandate but as a procurement reality: the people who would open this console are assessors and agency reviewers, and accessibility is a question they are institutionally trained to ask.

Which lands on the finding from this morning's audit. The KSI board cannot be operated by keyboard at all. The 46 rows are click handlers on table rows with no tab stop and no focusable child; tabbing from the top of the page goes through the nav, the two selects and two glossary terms, then wraps — never touching a single row. The recipes page has 39 more of the same. That is the one accessibility fact that would survive contact with a federal reviewer, and it is entirely fixable.

The real design question is audience, not style

rampscan's console is a dark, dense operator register — good for the person running scans. FedRAMP's ecosystem is light technical documentation, read by assessors and reviewers. Those are different rooms. The exports shipped in Q5 — the Certification Package Overview and the Ongoing Certification Report — are the artifacts that leave the building, and they currently have no presence in the UI at all.

That suggests a split rather than a repaint: keep the operator console as it is, and give the certification package its own reviewer-facing surface built to be read by someone who has never run a scan.

What preparing would take

Ordered — each step's output is the next step's input

  1. Re-vendor the schemas byte-exact

    Take upstream's bytes unmodified so the sha256 pin means what its comment says it means. Today the pin is pre-tripped by the project's own formatting, which makes the republication guard inert.

    Half a day · unblocks everything downstream

  2. Point the conformance checker at the published schemas

    rampscan already has a hand-rolled validator over the closed keyword set and a command that reads documents on disk. Run it across all eleven published CR26 schemas rather than the three currently vendored, and record what fails to compile or to validate. This is the step that produces something worth filing.

    Two to three days

  3. File what it finds as issues, with the tool named

    Follow issue #3's shape exactly: state the defect, state that it surfaced while building a provider tool that validates real documents, show the failing case. Do not open pull requests — the evidence says they are closed unmerged even when correct.

    A day, and it is the highest-leverage day here

  4. File the RFC-0033 comment

    Already tracked as #72 and due before 9 October. Phase 4 covers Class D and self-hosted/hybrid offerings, and FedRAMP has asked for targeted feedback over general commentary. rampscan's pipeline-source evidence model has something specific to say about what self-hosted validation can and cannot demonstrate — that is the comment, not a general endorsement.

    Deadline-bound · the only item here with an external clock

  5. Fix keyboard operability, then repair the repo's front door

    Make the board rows real tab stops. Then the description, the license detection, and topics — the three things that decide whether anyone arriving from an issue thread takes the project seriously. Repo settings are owner-blocked under #11.

    Two days, plus whatever the settings unblock costs

  6. Decide on a reviewer-facing surface for the certification package

    Only worth doing once steps 1–4 have established whether anyone upstream is paying attention. Scope it then, against real interest rather than anticipated interest.

    Deferred by design
